# Environment (Сервис изолированных бизнес-сред)

Сервис изолированных бизнес-сред для испытания агентов платформы **«Полигон»**. Моделирует внешнюю систему (CRM выездного обслуживания), в которой ИИ-агент работает с клиентами, услугами, временными окнами и заявками.

> [!NOTE]
> Согласно концепции проекта («Полигон / Испытательный стенд для ИИ-агентов»), сервис решает ключевую задачу: **отделить то, что агент сказал клиенту, от реальных изменений в бизнес-системе**, а также воспроизводить пограничные сбои (сетевые тайм-ауты, дубликаты, гонки).

---

## Основные задачи и возможности

1. **Изоляция данных разных сессий**:
   - Каждая тестовая попытка изолирована по `X-Session-ID` (или пути `/api/v1/sessions/{id}/...`).
   - Операции в одной сессии не видны и не влияют на другие сессии.
2. **Подготовка отдельного набора тестовых данных**:
   - Автоматическая инициализация реалистичными фикстурами предметной области (клиенты, мастера, временные слоты выездного обслуживания).
   - Поддержка кастомных начальных данных и возможность полного сброса сессии к исходному снимку (`POST /api/v1/sessions/{id}/reset`).
3. **Инструменты CRM для агента (через Runner)**:
   - Поиск клиентов: `GET /api/v1/clients`, `GET /api/v1/clients/{id}`.
   - Поиск доступных временных окон: `GET /api/v1/slots?date=...&service=...`.
   - Создание заявок с поддержкой идемпотентности (`Idempotency-Key`): `POST /api/v1/orders`.
   - Перенос визита и изменение адреса: `PATCH /api/v1/orders/{id}`.
   - Отмена заявок и автоматическое освобождение слота: `POST /api/v1/orders/{id}/cancel`.
4. **Воспроизведение управляемых сбоев (Fault Injection)**:
   - **`timeout_after_save`** (канонический сценарий из проектного брифа): заявка успешно сохраняется в БД, но вызывающая сторона получает HTTP 504 Gateway Timeout. Позволяет проверить, создаст ли агент дубликат при повторе.
   - `timeout_before_save`: тайм-аут до выполнения операции.
   - `delay`: искусственная задержка ответа.
   - `conflict`: ошибка конфликта данных (HTTP 409).
   - `server_error`: внутренняя ошибка сервера (HTTP 500).
   - `rate_limit`: превышение лимита вызовов (HTTP 429).
5. **Сохранение итогового состояния и журнала фактических изменений (Audit Log)**:
   - Фиксация всех мутаций: операция, состояние сущности до и после, параметры вызова, факт инъекции сбоя.
   - Снимок состояния (`StateSnapshot`): полный снимок данных сессии для Intelligence и Platform.
6. **Движок автоматической верификации (Assertion Engine)**:
   - Эндпоинт `POST /api/v1/sessions/{id}/verify` проверяет критерии успеха (отсутствие дубликатов, корректность финального адреса и временного окна, число активных заявок) и формирует протокол с доказательствами.

## API Спецификация

Все запросы принимают сессию через заголовок `X-Session-ID: <session_id>` либо путь `/api/v1/sessions/{session_id}/...`. Если заголовок не передан, используется сессия по умолчанию `default`.

### 1. Управление тестовыми сессиями и сбоями

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/api/v1/sessions` | Инициализировать сессию с фикстурами и правилами сбоев |
| `GET` | `/api/v1/sessions` | Список активных сессий |
| `GET` | `/api/v1/sessions/{id}/state` | Получить полный снимок состояния базы данных сессии |
| `GET` | `/api/v1/sessions/{id}/audit` | Получить хронологический журнал мутаций и событий |
| `POST` | `/api/v1/sessions/{id}/reset` | Сбросить сессию к исходному состоянию |
| `POST` | `/api/v1/sessions/{id}/faults` | Добавить динамическое правило сбоя |
| `DELETE` | `/api/v1/sessions/{id}/faults` | Очистить правила сбоев для сессии |
| `POST` | `/api/v1/sessions/{id}/verify` | Проверить критерии качества (число заявок, отсутствие дубликатов, адрес) |

При инициализации отсутствующие или `null` поля `clients` и `slots` используют стандартные фикстуры независимо друг от друга. Явный пустой массив `[]` создаёт пустой набор соответствующих сущностей. Тело должно содержать один корректный JSON-объект; при ошибке сервис возвращает `400` и сохраняет существующую сессию.

Правила сбоев активны по умолчанию. Неизвестный `fault_type`, отрицательные задержки или лимиты и `http_status` вне `400..599` (кроме `0` для значения по умолчанию) отклоняются с `400` до изменения сессии. Правила для `/api/v1/orders...` работают и через `/api/v1/sessions/{id}/orders...`; явно заданные полные пути также поддерживаются. Поле `active: false` явно отключает правило; политика одинакова для `fault_rules` при инициализации и для динамического добавления. `reset` восстанавливает исходные данные и обнуляет счётчики текущих правил, включая динамически добавленные; удаление правил выполняется через `DELETE .../faults`. `timeout_after_save` поддерживается для создания, изменения и отмены заявки: изменение сохраняется, ответ содержит ошибку, оба факта попадают в аудит.

При проверке `client_id` ограничивает все критерии и счётчики отчёта указанным клиентом. Без него проверяется вся сессия, а отсутствие дубликатов проверяется для каждого клиента. Адрес, дата и временное окно сравниваются с наиболее недавно изменённой активной заявкой. Если задан `expected_status`, выбирается наиболее недавно изменённая заявка любого статуса, что позволяет проверять отмену. При равных временах используются время создания и идентификатор заявки. Отсутствующая заявка даёт отрицательные assertions для запрошенных полей; окно сравнивается целиком, с удалением пробелов по краям.

### 2. CRM API для Агента / Runner

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/v1/clients` | Список клиентов |
| `GET` | `/api/v1/clients/{id}` | Информация о клиенте |
| `GET` | `/api/v1/slots` | Поиск свободных окон (`?date=2026-10-30&service=выездное+обслуживание`) |
| `GET` | `/api/v1/orders` | Список заявок (`?client_id=...&status=active`) |
| `GET` | `/api/v1/orders/{id}` | Детали заявки |
| `POST` | `/api/v1/orders` | Создание заявки (поддерживает `Idempotency-Key` в заголовке или теле) |
| `PATCH` | `/api/v1/orders/{id}` | Изменение параметров заявки (адрес, дата, окно, слот) |
| `POST` | `/api/v1/orders/{id}/cancel` | Отмена заявки и освобождение слота |

Операции создания, переноса и отмены атомарно обновляют заявку, бронирование и журнал изменений. Параллельные запросы с одним ключом идемпотентности создают одну заявку. Неудачное резервирование возвращает конфликт и сохраняет прежнее состояние. При передаче `slot_id` дата и окно должны соответствовать слоту либо отсутствовать — тогда они заполняются автоматически. Для переноса заявки с выбранным слотом нужно указать новый `slot_id`.

---

Содержимое событий аудита сохраняется как независимый JSON-снимок. Изменение исходного запроса после вызова сервиса или полученной копии журнала не меняет ранее записанные доказательства.

## Go SDK

Публичные контракты доступны в `poligon/environment/pkg/api`, клиент — в `poligon/environment/pkg/client`. Пакеты `internal` для интеграции не нужны:

```go
package main

import (
    "context"
    "log"

    "poligon/environment/pkg/api"
    "poligon/environment/pkg/client"
)

func main() {
    ctx := context.Background()
    c := client.NewClient("http://localhost:8081", "run-1")
    if _, err := c.InitSession(ctx, "run-1", nil, nil, nil); err != nil {
        log.Fatal(err)
    }
    order, _, err := c.CreateOrder(ctx, api.CreateOrderRequest{
        ClientID: "client-001",
        Address:  "г. Москва, ул. Тверская, д. 12",
        SlotID:   "slot-101",
    }, "request-1")
    if err != nil {
        log.Fatal(err)
    }
    log.Println(order.ID)
}
```

Пустой или состоящий из пробелов ID в `NewClient` и `SetSessionID` выбирает сессию `default`. Символы пути в ID сессии экранируются; завершающий слеш базового URL необязателен.

В Go поле `api.FaultRule.Active` имеет тип `*bool`: `nil` включает правило по умолчанию, указатель на `false` отключает его. В JSON сохраняется обычное логическое значение `active`.

## Сквозной сценарий: «Тайм-аут после сохранения»

Согласно странице 3 и 13 проектного брифа:
1. Тестовый API создаёт заявку, но возвращает тайм-аут (HTTP 504).
2. **Ошибка наивного агента**: агент не передаёт ключ идемпотентности и повторяет вызов создания заявки. В CRM появляются **две** заявки. Стенд фиксирует дефект `no_duplicate_orders_for_client: FAILED`.
3. **Исправленный агент**: передаёт `Idempotency-Key` или проверяет состояние. При повторе API возвращает уже созданную заявку без дублирования. Стенд фиксирует `PASSED`.

Данный сценарий полностью воспроизводится и автоматически проверяется тестом `TestCanonicalTimeoutAfterSaveScenario` в [test/integration_test.go](test/integration_test.go).

## Запуск и тестирование

### Запуск сервиса
```bash
cd Poligon/environment
go run ./cmd/server
# Сервис запустится на http://localhost:8081
```

### Запуск тестов
```bash
cd Poligon/environment
go test -race ./...
go vet ./...
```

### Пример проверки через curl

1. Создать сессию с инъекцией тайм-аута:
```bash
curl -X POST http://localhost:8081/api/v1/sessions \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "test-run-1",
    "fault_rules": [
      {
        "fault_type": "timeout_after_save",
        "method": "POST",
        "path_pattern": "/api/v1/orders",
        "http_status": 504,
        "max_triggers": 1
      }
    ]
  }'
```

2. Попытка создания заявки агентом (получает 504 Timeout, но запись сохранена):
```bash
curl -i -X POST http://localhost:8081/api/v1/orders \
  -H "X-Session-ID: test-run-1" \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "client-001",
    "address": "г. Москва, ул. Тверская, д. 12",
    "date": "2026-10-30",
    "time_window": "после 18:00"
  }'
```

3. Проверка состояния базы данных сессии:
```bash
curl http://localhost:8081/api/v1/sessions/test-run-1/state
```

4. Запрос верификации:
```bash
curl -X POST http://localhost:8081/api/v1/sessions/test-run-1/verify \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "client-001",
    "disallow_duplicates": true,
    "expected_active_orders_count": 1
  }'
```
